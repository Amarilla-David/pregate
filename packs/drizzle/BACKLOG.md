# drizzle backlog

Drizzle practices that are not a syntax invariant. Each row says what would have to be true for it to become one.

- **Migration SQL discipline.** Generated SQL under `drizzle/` has no TypeScript grammar, so no check reads it. A migration that drops a column the code still selects is a cross-artifact judgment: it needs the migration files plus the schema in one view.
- **RLS policies need SQL.** Row-level-security policies are SQL text (`USING (true)` is the open hole). Same reason as above: without a SQL grammar the rule cannot tell a permissive policy from a scoped one.
- **Index selection needs a workload.** Whether a foreign key or a `where` column needs an index depends on query volume and table size. The tree shows the column; it does not show the traffic.
- **Relations N+1 beyond loops needs flow.** DRIZ-REL-001 sees an awaited `db.` call syntactically inside a loop. A helper called in a loop that queries inside, or a `.map` with an async callback that queries, needs call-graph flow this engine does not do. Candidates if flow ever lands. The same limit applies to DRIZ-TX-001: a helper called from a transaction callback that queries the outer `db` is not seen.
- **Schema strictness candidates.** Serial and integer-family ids without `.primaryKey()` are now DRIZ-TABLE-002. Still left out: nameless `id: uuid()` / `id: text()` columns (DRIZ-TABLE-001 reads the `"id"` name argument); `date()` columns without a mode, because the default `string` mode returns the calendar date unchanged and has no timezone shift to report; a `fields` array that names the wrong columns (DRIZ-REL-002 checks presence, and the relation config type already requires `references` beside `fields`); DDL hidden behind a variable instead of a literal (DRIZ-MIG-001 reads the call text, so this needs value flow).
- **Where-string follow-ups.** DRIZ-SQL-001 fires on a leading string or template in `where`. `and()`/`or()` only accept SQL wrappers, so a string inside them is a type error, and a `sql` template inside them parameterizes. The only raw path inside a helper is `sql.raw`, which DRIZ-RAW-001 already reports anywhere. No new shape is left to add.
- **Unbounded relational queries.** DRIZ-LIMIT-001 watches the `select().from()` chain. `VP-FIND-MANY-001` matches any `.findMany(` call, including `db.query.users.findMany()`, and accepts Drizzle's `limit`. A Drizzle-native copy would report the same calls twice. The remaining gap is a `limit` that appears only on a nested `with` relation, which VP-FIND-MANY-001's word match accepts as a bound on the whole query.
- **Split query builders on delete/update (`DRIZ-DELETE-001`, `DRIZ-UPDATE-001` limit).** `DRIZ-DELETE-001` and `DRIZ-UPDATE-001` require `.where(...)` in the same call chain as `db.delete(table)` or `db.update(table).set(...)`. Queries stored in a variable and filtered later via `.$dynamic()` require multi-statement flow tracking.
